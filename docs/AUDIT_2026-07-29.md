# Pełny audyt platformy — 2026-07-29

Zakres: architektura, kod, zależności, produkcja, SEO, CRM, newsletter, wydajność, bezpieczeństwo, UX klienta i dokumentacja.

## 1. Wniosek zarządczy

Platforma jest szeroka funkcjonalnie i realnie generuje leady oraz zamówienia. Dzisiejsze zamówienie jest pozytywnym sygnałem lejka. Nie ma jednak podstaw, by opisywać całość jako „100% bezpieczną i zoptymalizowaną”: główne ryzyka to dynamiczny publiczny HTML, wolny TTFB, dług TypeScript/ESLint, podatne zależności, tokeny w `localStorage` oraz nieukończone porządkowanie SEO.

Najwyższy zwrot biznesowy daje kolejność:

1. nie tracić leadów i prawidłowo obsługiwać zgodę;
2. utrzymać sprawny checkout;
3. skrócić odpowiedź publicznych stron;
4. usunąć błędy technicznego SEO;
5. domknąć bramki bezpieczeństwa i jakości;
6. mierzyć lead → zamówienie → przychód.

## 2. Materiał i metoda

Sprawdzono:

- repo bazowe `c0fd4e5`;
- około 170 stron, 300 handlerów API, 114 komponentów i 81 modeli Prisma;
- konfigurację Next, Netlify, middleware, auth, sitemap, blog i krytyczne formularze;
- załączony raport Ahrefs „Overview — Właśniewski” z 2026-07-28;

Audyt kodu nie zastępuje pentestu, testów obciążeniowych ani opinii prawnej.

## 6. Newsletter i prywatność

### 6.1. Stan przed zmianą

- opcjonalny checkbox istniał w checkout, ale nie był przesyłany;
- rejestracja zapisywała czas na `User`, lecz nie synchronizowała listy;
- brakowało tokenu i czasu rezygnacji;
- CRM nie pokazywał stanu zgody;
- polityka CMS mogła nie zawierać informacji newsletterowej.

### 6.2. Stan gałęzi

- jawna, pusta zgoda we wszystkich głównych wejściach;
- wersja, źródło, czas, IP, user-agent i token;
- synchronizacja `EmailSubscriber` / `User`;
- rezygnacja z konta i tokenem;
- CRM pokazuje stan;
- stała informacja w polityce prywatności.

### 6.3. Warunek wdrożenia

Najpierw wykonać migrację `20260729193000_add_newsletter_consent_evidence`, potem wdrożyć kod. Po wdrożeniu sprawdzić zapis i rezygnację na adresie testowym.

Przed pierwszą masową kampanią zweryfikować link rezygnacji w każdym szablonie, domenę nadawczą, retencję i umowy powierzenia. Raport nie jest poradą prawną.

## 7. Wydajność

### 7.1. Pomiar

Sekwencyjny crawl 51 URL wykazał głównie 200, ale zimne/no-cache odpowiedzi trwały około 4–8 s, czasem 9–10 s. `/mogilno` i `/sklep/albumy` zwróciły pojedynczy 502, a kolejne trzy próby były 200.

Nagłówki publicznego HTML:

```text
cache-control: private,no-cache,no-store,max-age=0,must-revalidate
age: 0
```

### 7.2. Przyczyna

Root layout i loader analityki używają `headers()` do rozpoznania hosta. To wymusza dynamiczny rendering drzewa, mimo deklarowanego `revalidate = 3600`.

### 7.3. Plan

1. osobna gałąź wydajności;
2. pomiar Web Vitals i TTFB bazowy;
3. rozdzielenie layoutu domen albo bezpieczne przekazanie kontekstu hosta;
4. cache wyłącznie publicznego HTML;
5. test braku wycieku danych klienta;
6. canary/preview;
7. porównanie p50/p75/p95 oraz 5xx.

Nie wolno dodać globalnego cache do panelu, konta lub API.

### 7.4. Dług frontend

- 133 pliki z `force-dynamic`;
- tylko około 20 deklaracji rewalidacji;
- około 68 plików z surowym `<img>`;
- bardzo duże moduły administracyjne, m.in. PageBuilder i edytor strony głównej.

## 8. Bezpieczeństwo

### 8.1. Pozytywne ustalenia

- root middleware odpowiada tylko za domeny, a API admin ma własne guardy;
- sprawdzony zbiór endpointów admin nie ujawnił rzeczywistego publicznego wyjątku;
- formularz kontaktowy ma limit i walidację;
- SMTP nie może powodować utraty leada;
- checkout weryfikuje pakiet i cenę po stronie serwera;
- endpoint wypisu nie ujawnia, czy token istnieje;
- działają podstawowe nagłówki bezpieczeństwa.

### 8.2. Ryzyka

| Priorytet | Ryzyko | Dowód | Zalecenie |
|---|---|---|---|
| P0 | Build ignoruje typy i ESLint | `next.config.mjs` | Zielone bramki etapami |
| P0/P1 | 18 podatności prod | 13 high, 5 low | Aktualizacja i test |
| P1 | JWT w `localStorage` | AuthContext/admin | HttpOnly cookie + CSRF |
| P1 | Brak jednolitej CSP | config | CSP z nonce/report-only |
| P1 | Publiczne GET bloga zwraca także drafty | API blog | Rozdzielić public/admin |
| P2 | 12 plików backup w `src` | inventory | Przenieść poza kompilację |
| P2 | około 943 `any`, 160 logów | inventory | redukcja i logger |

### 8.3. TypeScript

Pierwsza próba z domyślną pamięcią zakończyła się wcześniej OOM. Z `NODE_OPTIONS=--max-old-space-size=4096` kompilator zakończył analizę i zgłosił dużą pulę wcześniejszych błędów: PageBuilder, kalendarz, umowy, galerie, albumy, PDF i brakujące typy. Zmienione moduły newslettera, formularzy, bloga i sitemapy nie pojawiły się jako nowe źródła błędów.

Nie oznacza to pełnego PASS. Kryterium P1: `npm run typecheck` = 0 i usunięcie `ignoreBuildErrors`.

## 12. Warunki uczciwego zamknięcia

Pełny audyt jest wykonany jako analiza i lista dowodów. Pełne usunięcie wszystkich znalezionych problemów nie jest jednym bezpiecznym wdrożeniem — szczególnie cache, auth, zależności i typy wymagają osobnych, mierzalnych zmian.

Bieżącą zmianę można uznać za wdrożoną dopiero po migracji, preview, testach i produkcyjnym smoke. Do tego czasu status to „zaimplementowane w gałęzi, oczekuje na wdrożenie”.
